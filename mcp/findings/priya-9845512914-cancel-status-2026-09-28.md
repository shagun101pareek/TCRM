## Which workflow

crm-mongo-sync only copies TeleCRM into `telecrm`. It mirrored In Pipeline. It does not write the CRM stage.

The new sync workflow does not map a plain patient-request cancel to In Pipeline. In Pipeline is forced only for a reschedule (`rescheduledFrom` / `rescheduledTo` / reason containing RESCHEDUL). With dashboard `LEAD` and a current stage of Session booked, the exported Finalize rule would choose Fresh, because Session booked is not in the preserved lead-status list. This cancel does not match the reschedule detectors. `new-telecrm` was updated about 0.4s after TeleCRM already showed In Pipeline, so sync recorded the new stage.

WF3 maps `BOOKED_*` → Session booked and `LEAD` → Fresh. A return to LEAD would push Fresh, not leave Session booked, and not write In Pipeline. The observed stage is In Pipeline, so WF3 did not leave this lead on Session booked.

The In Pipeline write is one second after the cancel. That timing matches an update made on the TeleCRM side at cancel time (agent, or a live automation that is not the exported cancel rule). The cancel → In Pipeline mapping in `mcp/findings/cancel-reschedule-telecrm-mapping.md` is still a proposal in this repo.
